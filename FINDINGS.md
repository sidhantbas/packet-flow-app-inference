## Dataset and features

What the released files contain, how the columns are defined, and what is excluded.

- 411 flows in total (247 train, 83 validation, 81 test), from one phone over about 44 minutes (`start_rel` spans 0 to 44.6 min).
- Both tasks share the same flow_ids and splits. Train and validation label counts match both metadata.json files (verified on 2026-09-29).
- Facebook has only 8 train, 3 validation and 2 test flows, and scores 0 on the task 1 validation split in the baseline (0.40 on task 2).
- `server_port` is 443 for 409 of 411 flows. The two exceptions are port 80 over TCP: flow_000535 (validation, x) and flow_001060 (test). The column carries almost no information and is dropped.
- `start_rel` stays excluded (experiment 002). Under 50-fold CV it adds +0.003 on task 1, which is no effect. On task 2 it adds +0.013, which is inside the fold noise (std 0.067) but consistent in 9/10 repeats, and the gain comes mostly from x and mozilla. That pattern looks like recording-time leakage, not a real traffic signal. The +3.8 points it seemed to add on the validation split in 001 were noise from that split.
- **Feature definitions decoded from the released data (2026-10-01), needed for any own capture:** burst = packets separated by gaps < ~1.0 s (prefix-5: burst_count = 1 for every flow with max_iat <= 0.78 s, >= 2 for every flow with max_iat >= 1.003 s; a 1.0 s threshold fits 100% of flows); flows have >= 5 packets (smaller flows dropped); bidirectional, 'up' = from the phone; durations up to 1304 s (no short active timeout); std = population std; duration = mean_iat x (packets - 1); start_rel and flow_id identical across tasks. Still unknown: idle timeout, exact 5-tuple, whether sizes are IP or payload lengths.
- Experiment 038: field audit. Unused by both pipelines: server_port, start_rel, split, flow_id (as a feature), metadata (test label counts forbidden). Tasks share all 411 flows. When the production models disagree (7.5% of held-out predictions), Task 1 is right 148 times vs Task 2 55. Task 2 outputs inside Task 1 hurt (features -0.0062, tiebreaker -0.0134). No unused signal left.
- `bytes_per_packet_{up,down}` equals `mean_pkt_size_{up,down}`, so do not add it again. Monotonic transforms (log1p) do nothing for tree models.
- **Ceilings (experiment 004):** no train+validation flows share an identical 17-column vector in either task, so the exact-duplicate ceiling is 1.0. Using only the 12 size/count columns (no timing), task 1 still has no mixed groups. Task 2 has 7 mixed groups covering 80 flows, giving a **macro F1 ceiling of 0.930** (facebook 0.857, instagram 0.900). The largest mixed groups: youtube 24 + google 2 (UDP 2762/2666 B), and x 30 + mozilla 5 + youtube 2 (TCP 794/140 B). The current task 2 score of 0.676 is far below that, so the gap is model error, not a hard limit of the features.
- The two port-80 flows (flow_000535, validation, x; flow_001060, test) look like the same periodic low-volume connection, with identical first-5-packet sizes.

## Evaluation, validation and noise

How we measure, and how much a single split or an 81-flow test can move.

- CV baseline (RF, experiment 002): task 1 macro F1 0.733 ± 0.079, task 2 0.676 ± 0.067 (fold std). Facebook F1 is 0.49 on task 1 and 0.36 on task 2, both ± ~0.29. Facebook causes most of the macro F1 noise.
- A leading entry reportedly scores 0.97. The **Validation Phase leaderboard scores the public validation labels** (templates/challenge_phase_1_description.html): our own final models, trained on train+validation, score 1.000 / 0.976 there (98.8 / 100), so a 0.97 in that phase says nothing about real skill. Check which phase a leaderboard number comes from. `flow_id` numbering is not a shortcut (1-NN on the number: 0.50). In the Final Test Phase (81 flows, 2 Facebook), a large jump over our CV level would need outside data (allowed if disclosed), many leaderboard probes, or luck. Keep selecting only by 50-fold CV plus confirmation seeds.
- **The validation gap is Facebook.** Trained on train only, our five other classes score 0.86–0.94 on validation (leader level), but Facebook is 0.00 on task 1 (predicted mozilla, google, mozilla) and 0.33 on task 2. With Facebook perfect, validation would be 0.912 / 0.890 (~90). Reason: 7 of 8 train Facebook flows are UDP; all 3 validation Facebook flows are TCP, long-lived (235–1122 s), tiny packets (77–182 B up), mean_iat 6–10 s. That TCP pattern (TCP, mean_iat > 3 s, duration > 100 s) is not Facebook-specific in train+val (google 13, mozilla 7, x 4, youtube 3, facebook 3). With only 2 test Facebook flows, each task's score swings by up to ~8 points on Facebook alone.
- Experiment 036: test flows have near-twins in the labelled set (18.5% within 0.05, vs 11.8% for normal-CV held-out flows), so **normal CV mirrors the test**; twin-aware CV (StratifiedGroupKFold, 303 groups at 0.05) is a stress test (all models ~-0.05 macro, ~-0.19 facebook). 028 and 034 keep their gains under it. Scoped H1 (`models.ScopedH1`: exact-opening override only outside facebook/instagram) passes rule v2 on 6 split sets with zero lost folds (+0.003 to +0.006); changes 0 current test predictions; not yet adopted.
- Experiment 039 (measurement only): flow_id numbers follow capture order exactly (Spearman 1.0 with start_rel); 78% of labelled flows sit in same-app runs (random order 42.5%), but kNN on capture order scores only 0.50 macro (facebook <= 0.18) and adding it to production costs -0.040 (Task 1) / -0.015 (Task 2). Not explicitly banned but contrary to "only statistical packet-flow features"; treat as off-limits.
- Experiment 040: on 81-flow resamples of production's held-out Task 1 predictions, macro F1 median 0.834 (5th-95th 0.737-0.917); our leaderboard 0.787 is at the ~21st percentile, the leader's 0.94 at the ~98.7th (P about 1-2%). One facebook flow flips Task 1 by 2-4 points. The Final Test Phase scores all 81 flows and is the official ranking (no hidden final set).
- Runtime: models are single-threaded and `cv.evaluate()` parallelises the 50 folds; a SoftVote run takes ~4 s on this Mac.

## Models and ensembles

Learners, settings, experts and combinations.

- Experiment 003: none of these variants beats the baseline RF under the rule "Δ > 0 and ≥ 35/50 fold wins": balanced_subsample, log1p + bytes_per_packet, ExtraTrees, small LightGBM, and fold-internal oversampling of facebook/instagram. Nearest misses: ExtraTrees on task 1 (+0.015, 34/50) and LightGBM on task 1 (+0.023 but only 26/50). **Baseline RF stays the default.**
- Experiment 004: the soft-voting ensemble (mean proba of RF + ExtraTrees + LightGBM from 003) gets task 1 0.771 (+0.038, **34/50**, better on every class, Facebook 0.58) and task 2 0.686 (+0.010, 29/50). It is **not confirmed** (misses by one fold on task 1) but is the strongest task 1 candidate. Per-class probability multipliers tuned by nested CV **hurt** in all four settings (up to −0.039 on task 2, with Facebook dropping to 0.18), so do not use them at this data size.
- Experiment 016: memorisation is right for this data. min_samples_leaf 2–3 raises the task 2 error on seen vectors (0.063 → 0.09) and costs ~0.02. Adding logistic regression + kNN (log1p + standardised) as members lowers the unseen-vector error 0.415 → 0.398, task 2 +0.006 (near miss), but kNN (no class weights) costs task 1 Facebook 0.075.
- Experiment 017: novelty gating (trees for seen task 2 vectors, + logistic regression/kNN for new ones) equals 016 exactly (+0.006, near miss); trees already dominate seen vectors. Round 2 is closed: champions task 1 0.771, task 2 0.754.
- Round 3 (018–020, nothing adopted): ensemble settings are flat (max_features, LightGBM leaves, 1000 trees all within ±0.011; 1000 trees passed once at seed 2026 and failed confirmation). Stacking with a learned logistic combiner hurts (task 1 Facebook −0.17 to −0.24; inner folds hold ~5 Facebook flows). Task 2 facts: every flow has exactly 5 packets; `std_pkt_size` is the population std, so directions with ≤ 2 packets have exactly known sizes (mean ± std); adding them explicitly changes nothing.
- Experiment 024: TabPFN v2 (local `tabpfn` 9.0.0, ungated v2 weights, CPU) alone is worse (Task 1 0.769, Facebook −0.21; Task 2 0.734). As a third Task 1 member (1/3 weight, facebook kept) it gains +0.014 to +0.018 on all 5 seeds but misses rule v2 on cv_seed 2028 (31/16) and 2029 (30/18): not adopted. If ever adopted, disclose it as an outside pretrained model.
- Experiment 025: self-training (confidence ≥ 0.9, no fb/ig pseudo-labels, pool = held-out + test features) does nothing (Task 1 −0.006, Task 2 0.000): the confident pseudo-labels are flows the model already gets right.
- Experiment 029: behaviour concepts (first-principles flags: -0.000; KMeans kinds of run: -0.008) do not help Task 1: every app makes quick exchanges, keep-alives and uploads, so a kind of run does not identify the app.
- Experiment 032: app USPs (one-vs-rest AUC): instagram bursts 0.91; youtube large upload packets 0.80; google large opening packets ~0.75; mozilla small everything 0.15; x TCP + tiny opening 0.17; facebook opening receives more than it sends 0.20. A naive Bayes on 5 quantile levels per feature is much worse (0.64 / 0.53 alone; -0.040 / -0.007 as a member): related columns double-count and coarse levels lose detail.
- Experiment 033: gated behaviour hybrid (p_model x p_NB^lam where margin < tau; lam, tau by nested inner CV, lam = 0 allowed) is worse (Task 1 -0.012, Task 2 -0.002): inner selection on ~176 flows picks up luck in ~60% of folds.

## Specialists, gates and verifiers

Second-stage decisions for confusable pairs and the Meta family.

- Experiment 012: class weights. Task 1 needs `balanced` (Facebook −0.090 without). Task 2 without weights: +0.012 (24 W / 5 L / 21 T, inconclusive under the rule), almost all from Instagram (+0.075, 19/0), because balanced weights push the shared Instagram/Facebook first-5 pattern to Facebook. `SoftVote(class_weight=...)` accepts "balanced", None or "sqrt".
- Experiment 013: a google-vs-youtube second-stage specialist does nothing (|Δ| ≤ 0.005). A standalone google-vs-youtube model reaches AUC 0.89 (task 1) / 0.92 (task 2), balanced accuracy 0.82 / 0.86, with or without ratio features. The 6-class model already separates the pair about as well as a dedicated one can, so do not spend more effort on google/youtube features.
- Experiment 014: the facebook/instagram specialist hurts task 1 (Facebook −0.047 to −0.081) but helps task 2 (facebook +0.02–0.04, instagram +0.06–0.09 on three fold sets). 012's unweighted SoftVote also passes rule v2 on task 2, but the specialist beats it head to head on all three fold sets.
- Experiment 015: mozilla vs x on task 2. A pair-only model gains AUC with timing (0.945 → 0.976) but hardly balanced accuracy (+0.01). A timing-aware mozilla/x specialist only swaps errors (mozilla → x 50 → 38, x → mozilla 16 → 36; Δ ≈ 0). The 007 increase in mozilla → x was a shift inside the pair, not a net loss. `models.MultiSpecialist` chains several pair specialists.
- Experiment 034: hierarchical Meta gate on the two-clerks Task 1 model lifts facebook F1 0.59 -> 0.67 (+0.082, 14/2 folds) but costs instagram -0.029 (1/16); net +0.0105, 15/11/24, not adopted. 034b (rescue-only) is identical: the gate only moves flows from outside Meta into Meta (40 per seed-2026 run; facebook recall 0.59 -> 0.72, instagram precision 0.81 -> 0.74); +0.0006 to +0.0105 on seeds 2026-2030, fewer winning folds on 4 of 5. Facebook/Instagram share QUIC openings; bodies differ (Instagram heavy; Facebook TCP keep-alives, slow QUIC trickles, short QUIC fetches that look like google).
- Experiment 084: pair verifiers. A google-vs-x verifier for production's x calls (balanced SoftVote on google + x rows) plus 083 (arm ALL) is rule v2 BETTER on all five seeds (mean +0.0050; google, x, instagram up; facebook 0). google-vs-mozilla verifiers fail (they break more than they fix). The ALL test file differs from 87.77 in one Task 1 flow (`flow_000095` x → google): `submissions/best-88.11-production-084/`. **Adopted 2026-10-09 (user decision)** as `models.task1_pair_verifiers`.
- Experiment 089: the near-miss bundle (065 R rest-of-flow expert + 087 instagram-protecting doorman + 036 scoped H1, on top of 084 ALL) is rule v2 BETTER on all five never-used cv_seeds 2031-2035 (mean +0.0141; the members' gains add up because they fix different classes). Test file differs from 88.11 in 2 Task 1 flows: `submissions/production-089-bundle/`. **Adopted 2026-10-10 (user decision)** as `models.task1_bundle`. Task 2 bundle (085 T2-MG) fails (2 of 5).

## Task 2 timing

Why the five timing columns are dropped in Task 2.

- Experiment 007: timing columns hurt task 2 (dropping all five: +0.051, 40/50, every class better, x → google errors 30 → 4, but mozilla → x 33 → 50). Task 1 `min_iat` is 0 in 98% of flows; dropping it does nothing. Exact identities in both tasks: duration = mean_iat × (packets − 1), bytes = count × mean size, so packets/s is redundant with mean_iat. A time-blocked split is unusable (x: 62 early / 11 mid / 0 late flows).
- Experiments 008–011 (round 1 of the to-do list, nothing adopted): the ratio families (relative timing, bytes/s, burst density, downstream share, packet-size CV) do nothing on task 1 and timing ratios cost task 2 ~0.05. CatBoost (alone, categorical transport, or as a 4th SoftVote member) is inconclusive; unweighted CatBoost is the best task 2 variant (+0.015, 27/50), a hint that balanced class weights hurt task 2. Permutation (50 folds): task 1 timing is the Facebook signal (costs Facebook 0.40 when shuffled), task 2 is mostly upstream columns. 74% of task 2 held-out flows have an exact twin in training and are 96% right; **68% of task 2 errors are on never-seen vectors, mostly google/youtube**. `start_rel` alone scores 0.51 (1-NN) and lowers the task 2 champion to 0.719.

## Errors, facebook and instagram

Where the errors are and why facebook is hard.

- Experiment 021: in CV on train+validation the champion predicts the long TCP Facebook flows as facebook 10/10, 9/10, 5/10, so the submission (trained on train+validation) covers that Facebook type. Remaining Facebook misses: two UDP flows that look like google (flow_000799, flow_001145) and one short TCP flow (flow_000231). Explicit TCP-signature features hurt task 1 Facebook (−0.046).
- Task 1 error decoding (2026-10-01): 44/330 flows wrong in >= 5/10 CV repeats (google 19, youtube 13, facebook 5, instagram 4); they sit among other apps' flows (17% same-app among 5 nearest neighbours vs 73%); accuracy barely depends on size or transport. The Task 2 model gets 22 of them right and vice versa. Experiment 028 (two clerks: whole-run + opening expert, Meta decided by the whole run): +0.005 to +0.013 on all 5 seeds, 58-65% wins, not adopted.
- Experiment 031 (error audit): most google/youtube errors have a nearest training row with the predicted label (Task 1 131/175, Task 2 138/189; Task 2 also 30 exact duplicates); Task 2 duplicate-conflict accuracy bound 0.958 (Task 1 has no duplicate vectors); pooled headroom of any decision-rule change <= 3 (Task 1) and <= 6 (Task 2 fb/ig stage threshold) errors in 3,300; the stage's facebook probabilities are bimodal (< 0.3 or >= 0.7). No candidate justified.
- Experiment 035: H1 (trust exact opening twins) is rejected: -0.0345 macro F1 (27 fixed, 32 broken; shared Meta openings flip facebook to instagram). The 4 facebook/instagram errors have no exact twin; near matches point to both apps. **Twin leakage:** forcing near-identical facebook fetches 000809/001168 into one fold drops facebook F1 0.674 -> 0.521 (macro 0.828 -> 0.801), so CV overstates Facebook; prefer twin-aware folds for Facebook estimates.
- Experiment 037: nearest-twin override dropped. 15 test flows have a labelled flow within 0.05 (17 features); production already predicts all 15 twins' labels; in CV it changes nothing at <= 0.05 and 5 predictions (+0.001) at 0.08. Twin rule and scoped H1 touch disjoint rows.
- Main confusions: facebook ↔ instagram (in task 2 almost exclusively between the two), google ↔ youtube (the largest by volume), x ↔ mozilla. In task 1, Facebook flows are much smaller and slower than Instagram flows (bytes, packet counts, burst_count, mean_iat). In task 2, 15 train+validation flows share one exact first-5-packet pattern (3 downstream packets, ~1656 B, std ~513.5, UDP) and all of them are Instagram (13) or Facebook (2). It marks the two apps as a group but cannot separate them.
- google vs youtube: in task 1 the best separators are mean_pkt_size_up (youtube larger), up_down_byte_ratio and mean_pkt_size_down (google larger), each ≤ 0.44 separation. Timing features do not help. In task 2 all separators are weak (≤ 0.35).

- Experiment 126 (2026-10-21): production Task 1 leaks only 3 of 30 Meta flows per repeat into non-Meta classes (mostly instagram → youtube), and those flows are light (median 0.6 kB down vs 22 kB for Meta flows called Meta): by volume they look like x or google, so a volume rescue reaches 2 leaked predictions but 86 correct non-Meta ones; all rescue arms lose.

- Upload 10 (2026-10-21, candidate 127): restoring Task 1's instagram count to the training mix's expectation (099 rule D, 3 flows switched to instagram) scored 90.85 (Task 1 about 0.912, from 0.822) although the rule loses in CV (−0.0169): the test set's instagram deficit is outside the CV range (099), so a count correction can pay off there. One upload on three flows; information, not evidence.

## Captures and outside data

Own captures and their limits (details in the capture handover).

- Experiment 041 (feasibility of own captures, understanding only; report): no-go. Task 1 outside data is allowed with disclosure; Task 2 is literally limited to its own files; our team rule bans captures anyway. Decoded: `up` = from the phone; Task 2 = first 5 packets in time order, both directions; sizes = Ethernet frame lengths over IPv4 (60-B padded minimum, 1294 = Meta mvfst 1252-B datagrams); population std for sizes and gaps; burst gap ~1.0 s; idle timeout > 240 s; µs timestamps; the client's first TCP packet is an unexplained 145–175 B. 7 Facebook/Instagram traffic types (keep-alive, short TCP, short QUIC fetch, QUIC burst, slow trickle are facebook's; media download, upload-heavy are Instagram-only). Labels look destination-based: 6/11 facebook flows start within 10 s of an Instagram flow (other apps 5–11%).

- Experiments 120-123 (2026-10-19/20): process-attributed labels (120) and Charles's independent 364-flow subset agree on every flow (122), yet every capture version fails gate 2 (AUC 0.945 clean, 0.965 Charles's strict subset; 121, 123): sizes and counts alone separate captures from challenge flows (0.92-0.94), and captured Meta flows sit nearest to challenge google flows. The gap is the device/app population, not the preprocessing (receipt). Training on them at Charles's low doses still lowers facebook on every seed (124), because the facebook/instagram contrast itself is reversed on our phone: there facebook flows are larger than instagram flows, in the challenge data smaller (125: transfer AUC 0.24-0.58).

## Since 9 October (experiments 052-101)

Short summaries; the linked logs and reports hold the evidence.

- **Captures do not transfer** ([052](experiments/052_iphone_pilot.md)-[059](experiments/059_android_signature.md), [063](experiments/063_capture_android_filtered.md), [091](experiments/091_public_facebook_data.md); capture handover): our iPhone captures, our Android captures and a public August 2026 Android dataset agree with each other and differ from the challenge data in the same way: the client's first packet of a connection is about 70-100 B larger in the challenge data. Training on captured flows cut facebook F1 by 0.07 to 0.38.
- **Error floor** ([074](experiments/074_error_floor.md), [079](experiments/079_pipeline_audit.md)): 65% (Task 1) and 81% (Task 2) of errors are on flows whose nearest training flow belongs to another app; all model-limited errors together are worth about +1 CV point. Task 2's loss is mostly irreducible on its 12 columns.
- **Pair verifiers and the bundle** ([083](experiments/083_instagram_google_verifier.md), [084](experiments/084_pair_verifiers.md), [089](experiments/089_near_miss_bundle.md), [097](experiments/097_reliability_089_vs_084.md)): re-deciding instagram and x calls against google helped (+0.005, five seeds); three near-misses combined helped more (+0.0141 on five never-used seeds) and the gain survives twin-aware folds. Only the exact-opening override has consistent evidence on its own.
- **Decision rules** ([061](experiments/061_task1_f1_threshold_rule.md), [062](experiments/062_task1_nonmeta_thresholds.md), [067](experiments/067_meta_twins_threshold.md), [088](experiments/088_exam_savvy_clerk.md), [095](experiments/095_disclosed_count_simulation.md), [096](experiments/096_task2_timing_tiebreaker.md); [decision guide](data_limited_analysis/decision-making-guide.md)): cutoffs learned from about 9 facebook rows per fold follow noise (a winner's curse); the leader's described calibration and count matching, simulated without test counts, stays below production.
- **Data-limited** ([093](experiments/093_data_limited_analysis.md); [report](data_limited_analysis/REPORT.md)): the learning curve is still rising (+3.6 points from 80% to 100% of training rows), label noise costs about nothing, and derivable features, self-training and monotonic constraints all tie.
- **Opening stamps** ([090](experiments/090_stamp_catalogue.md)): exact opening sizes can be decoded from the statistics (verified on 100 of 102 TCP openings); 4 of 11 facebook flows carry a facebook-only stamp, the other 7 share every stamp with another app.
- **The leaders' described levers do not fix facebook/instagram for us** ([119](experiments/119_leader_meta_decomposition.md)): even each fold's true class counts lower Task 1 facebook F1 when probabilities collide; capture-time smoothing hurts most; cross-task joint decoding helps Task 2 (+0.0135) only by using Task 1 information, which condition 2 forbids.
- **Opening timing carries no facebook/instagram signal** ([118](experiments/118_conditional_timing.md)): adding it to Task 2's specialist lowers the pair AUC and macro F1 in ordinary, exact-grouped and session-grouped folds (WORSE 15 of 15). Session-grouped folds barely lower production (0.74 vs 0.77), so memorised openings recur across capture sessions.
- **Task 2 is largely memorised openings** ([117](experiments/117_grouped_109b.md)): keeping exact copies of an opening in one fold cuts production Task 2 macro F1 from about 0.76 to 0.48 (0.24 with near-duplicate groups); 63% of test flows have an exact single-label twin (115), which explains the high Task 2 test score (0.905). 109 B's gain survives grouping but is a two-value size lookup (1365 B → facebook, 1367 B → instagram) on two facebook pairs.
- **Identifiability and artefacts** ([115](experiments/115_identifiability_and_artefacts.md)): the app signal is mostly an opening packet-size fingerprint of the capture setup; facebook and instagram share Meta's fingerprint (Bayes error at least about 24% on the first 5 packets, about 11% on whole-flow columns); session context is strong (instagram's nearest flow in capture time is instagram 9× chance) but off-limits; test flows have more exact twins than CV folds (63% vs 54%).
- **Facebook audit** ([098](experiments/098_facebook_audit_and_final_candidate.md)): 22 of 31 facebook errors and 26 of 40 false facebook calls have every expert wrong; two facebook flows succeed only when each other's near-twin is in training.
- **Test-set instagram shortfall** ([099](experiments/099_class_count_deficit.md)): Task 1 predicts 2 instagram test flows where the stratified split implies about 5, a shortfall never seen in 50 CV folds (likely the largest Task 1 test loss, about 3.6 points if 3 are missed). Filling the count by instagram score is not justified: 27% of flips right, Δ −0.017.
- **Cross-task Meta rescue** ([100](experiments/100_cross_task_meta_rescue.md); [insight note](docs/reports/closing-the-f1-gap-2026-10-12.md)): when Task 2 calls instagram and Task 1 calls a non-Meta app, Task 1 is wrong 137 of 138 times (ordinary folds); production's instagram safeguards (087 revert, 084 verifier) push these Meta flows out. Relabelling them facebook: +0.011 on fresh seeds (positive 5 of 5, BETTER 1 of 5), +0.030 on twin-aware folds (BETTER 5 of 5); instagram as the label does nothing. Not a pass by the frozen rule; adopted in production as a deliberate exception (user decision 2026-10-12): `models.task1_cross_task`, CV 0.857; one test change (flow_000223 youtube → facebook), file `submissions/production-100-cross-task/`, not uploaded.
- **Test-time averaging** ([101](experiments/101_test_time_averaging.md)): predicting each flow with timing scaled by 0.85-1.18 and taking the majority label changes 10 of 1,650 held-out predictions (no seed BETTER) and no test prediction: production's labels are stable under timing noise, so its errors are not near decision boundaries.
- **Platform and leaderboard, read 2026-10-13** ([reverse engineering](docs/reports/leaderboard-reverse-engineering-2026-10-13.md)): limits 5 submissions a day, 50 a month, 100 in total (the "7 used, none left" count was wrong); 12 Final Test Phase submissions on the platform, 8 in our records; the board shows each team's best submission among those ticked "Show on leaderboard" (ours: 87.24, rank 8 of 8); leader 94.98 (Task 1 0.96, Task 2 0.94). The three teams that describe their method all use the published test class counts; one also smooths predictions over capture time and uses an SNI-length proxy. All three ingredients are excluded by our rules; count matching did not help our model in CV (095, 099).
- **Leader reproduction 1: Infralibre** ([102](experiments/102_flowlens_reproduction.md)): their recipe (balanced first-5 ensemble, calibration, disclosed counts) is WORSE than our Task 2 production on all five never-used seeds; disclosed counts are no better than training-share counts. On our test file it would move 6-7 Task 2 predictions off our x surplus, which is consistent with their 0.94 but not supported by cross-validation.
- **Leader reproduction 2: LLM_ops** ([103](experiments/103_lookup_ensemble_reproduction.md)): the Lookup-Ensemble-v7 ladder is WORSE than production on all five never-used seeds in both tasks (−0.065 each); their base starts 0.07-0.10 lower. Capture-time smoothing hurts both tasks, so the excluded signal does not explain their score either. Prior correction β = 0.25 helped Task 1 (+0.006) only.
- **Leader reproduction 3: RahmaniJ** ([104](experiments/104_early_flow_reproduction.md)): first-5 features only, one prediction set for both tasks, count assignment: WORSE than production on all five never-used seeds (Task 1 −0.148, Task 2 −0.064); the published counts add +0.001 over training shares. **None of the three described leaders beats our production in cross-validation** (102-104).
- **Leader reproduction 4: Infralibre v9, with due diligence** ([105](experiments/105_pairswap_reproduction.md)): the cross-view ensemble with a count-preserving consensus swap is WORSE than production on all five never-used seeds; a label-blind swap breaks 2-3 correct flows for each one it fixes, and the +2 correct flows their score change implies came out of a blind swap in only 1-2% of batches. Leaderboard notes should be read as claims, not as methods.
- **Capture time is not the leaders' secret** ([107](experiments/107_temporal_label_neighbours.md), measurement only): copying the labels of training flows opened within 0.5-2 s breaks about three correct predictions per fixed one in both tasks; flows opened together often go to different services (labels follow the destination). Prior correction β = 0.25 on our production adds +0.001 ([106](experiments/106_prior_correction_production.md)).
